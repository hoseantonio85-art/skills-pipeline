# Input Contract

## 1. Обязательный вход

Предпочтительный вход:

```text
01_product_brief.md
```

Минимально он должен содержать:

- task ID или понятное название;
- проблему;
- цель;
- основного пользователя;
- текущий сценарий или описание отсутствующего сценария;
- ожидаемый пользовательский результат;
- scope;
- out of scope;
- ограничения;
- открытые вопросы;
- использованные источники;
- статус.

## 2. Допустимые статусы

### `APPROVED_FOR_UX`

Можно начинать полный UX-этап.

### `APPROVED_FOR_ANALYSIS`

Можно начинать только после проверки, что критичные бизнес- и системные вопросы
закрыты или не влияют на UX.

### `DRAFT_*`

Разрешён только режим `explore`.

### `BLOCKED_BY_CONTEXT`

Не создавать финальное UX-решение.

### Статус отсутствует

Считать вход неподтверждённым. Уточнить у владельца или использовать режим
`explore`.

## 3. Blockers входа

Остановить финальное проектирование, если неизвестно хотя бы одно:

- какая проблема решается;
- кто основной пользователь;
- какой результат должен получить пользователь;
- что входит в scope;
- какое решение или действие является центральным;
- какие критичные правила влияют на сценарий;
- существует ли конфликт между источниками, который меняет flow.

## 4. Что можно уточнить на UX-этапе

Допустимо уточнять:

- точку входа;
- порядок действий;
- информационный приоритет;
- переходы;
- вспомогательные роли;
- состояния;
- edge cases;
- feedback;
- необходимость AI;
- выбор page/modal/drawer.

## 5. Что должно вернуться на анализ

Вернуть задачу на product/business/system analysis, если требуется определить:

- право пользователя на действие;
- юридически значимый статус;
- обязательное согласование;
- расчёт;
- доменный переход состояния;
- источник данных;
- API или интеграционный контракт;
- принадлежность сущности;
- ответственность сервиса;
- необратимое последствие.

UX не должен изобретать эти правила.
