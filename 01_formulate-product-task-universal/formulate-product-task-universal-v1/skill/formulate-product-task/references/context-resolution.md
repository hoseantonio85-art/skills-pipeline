# Разрешение продуктового контекста

## 1. Цель

Этот документ определяет, как универсальный skill выбирает и подключает продуктовый контекст.

Контекст отделён от методики. Изменение фактов о продукте не требует изменения `SKILL.md`.

## 2. Поддерживаемые значения

### `norm`

Контекст продукта NORM.

Текущий предполагаемый provider: `local_repository`.

### `orm`

Контекст продукта ORM.

В первой версии является заготовкой со статусом `planned`. Наличие записи в registry не означает, что контекст подключён.

### `none`

Работа без продуктового контекста.

Используются только:

- сообщения пользователя;
- приложенные к текущей задаче материалы;
- явно переданные ссылки или файлы.

## 3. Порядок определения контекста

Проверяй строго в таком порядке.

### Шаг 1. Явный выбор пользователя

Распознавай формулировки:

- `контекст norm`;
- `для NORM`;
- `используй ORM`;
- `без контекста`;
- `только по моим вводным`.

Явный выбор пользователя имеет приоритет над настройками проекта.

### Шаг 2. Уже выбранный контекст текущей задачи

Если пользователь ранее в этой же задаче явно выбрал контекст и не менял его, продолжай использовать его.

Не переноси выбор автоматически между несвязанными задачами или новыми сессиями.

### Шаг 3. Project-level selector

Попробуй прочитать:

```text
.gigacode/product-context.yaml
```

Если файл существует и содержит один валидный `context_id`, используй его.

### Шаг 4. User-level registry

Попробуй прочитать:

```text
~/.gigacode/product-contexts.yaml
```

Registry описывает доступные профили и providers, но сам по себе не выбирает контекст задачи.

### Шаг 5. Спросить пользователя

Если после шагов 1–4 контекст не определён однозначно, задай один вопрос:

```text
Какой продуктовый контекст использовать?

1. norm — продукт NORM
2. orm — профиль ORM; может быть ещё не подключён
3. без контекста — использовать только ваши вводные и приложенные материалы
```

Не начинай продуктовую постановку до ответа, потому что выбор влияет на достоверность результата.

## 4. Проверка доступности выбранного контекста

### Для `local_repository`

Проверь:

1. задан ли `provider.root`;
2. не является ли путь placeholder;
3. существует ли директория;
4. доступен ли manifest;
5. совпадает ли `context_id` manifest с выбранным контекстом;
6. доступны ли обязательные документы;
7. указан ли статус актуальности.

Не утверждай, что путь существует, если не удалось его проверить.

### Для `confluence_mcp`

Проверь:

1. подключён ли указанный MCP server;
2. доступен ли space/root page;
3. можно ли получить context manifest или эквивалентный индекс;
4. достаточно ли прав для чтения.

Не пересказывай Confluence-страницы, которые реально не были получены через MCP.

### Для `none`

Не пытайся искать продуктовые документы автоматически.

## 5. Если контекст выбран, но недоступен

Сообщи конкретную причину:

- путь не настроен;
- репозиторий не найден;
- manifest отсутствует;
- MCP не подключён;
- профиль имеет статус `planned`;
- доступ запрещён.

Затем предложи ровно три действия:

```text
1. Указать или исправить источник выбранного контекста.
2. Выбрать другой контекст.
3. Продолжить без продуктового контекста.
```

Не переключайся на другой контекст молча.

## 6. Режим без контекста

Работа без контекста разрешена, если пользователь выбрал её явно.

Обязательные ограничения:

- пометить `context_id: none`;
- пометить `context_status: not-used-by-choice`;
- все сведения о продукте считать `owner-stated`, `attachment-confirmed` или `unknown`;
- не утверждать, что проверены существующие capabilities;
- не утверждать границы сервисов;
- не утверждать существующие бизнес-правила;
- не утверждать, что похожей фичи нет;
- не присваивать verdict `READY_FOR_UX`;
- максимально допустимый положительный verdict — `READY_FOR_ANALYSIS`;
- добавить обязательную проверку продуктового контекста на следующем этапе.

Работа без контекста не равна некачественной работе. Она означает ограниченную доказательность.

## 7. Частичный или устаревший контекст

Если часть документов отсутствует или имеет статус `needs-review`:

- продолжай, если проблема, пользователь и границы достаточно понятны;
- укажи `context_status: partial` или `needs-review`;
- не повышай достоверность утверждений;
- вынеси недостающие сведения в открытые вопросы;
- используй `BLOCKED_BY_CONTEXT` только для критичного пробела.

## 8. Фиксация выбора в результате

Каждый brief должен содержать:

```text
context_id
context_provider
context_status
context_root_or_resource
context_manifest
context_checked_at
context_revision
```

Если значение неизвестно, используй `unknown`, а не правдоподобную догадку.

Для локального git-репозитория по возможности фиксируй branch и commit SHA.

Для Confluence по возможности фиксируй page ID и дату/версию извлечения.
