# Политика источников для Product Task Brief

## 1. Основной принцип

> Лучше явно зафиксировать пробел, чем заполнить его правдоподобной догадкой.

Skill работает с логическими источниками, а не с жёстко заданными путями конкретного продукта.

Логические группы:

- product foundation;
- service map;
- service descriptions;
- roles;
- glossary;
- business rules;
- released features;
- constraints;
- decisions;
- materials of the current task.

Provider может быть локальным репозиторием или Confluence MCP.

## 2. Типы утверждений

### `source-confirmed`

Подтверждено реально прочитанным актуальным источником.

### `owner-stated`

Явно сообщено product owner в текущей задаче.

### `attachment-confirmed`

Подтверждено файлом или материалом, приложенным к текущей задаче.

### `needs-review`

Найдено в источнике, который требует актуализации.

### `assumption`

Рабочая гипотеза агента или команды.

### `unknown`

Данных нет.

Нельзя преобразовывать `needs-review`, `assumption` или `unknown` в факт при редактировании текста.

## 3. Метаданные контекста

По возможности каждый канонический документ должен иметь:

```text
status: current | needs-review | draft | archived
owner
last_reviewed
valid_from
source
authority
```

Если метаданных нет, статус документа считается `unknown`.

## 4. Приоритет источников

Приоритет зависит от типа утверждения.

### Текущее фактическое поведение

1. проверенная выпущенная реализация или release evidence;
2. актуальный канонический документ;
3. решение владельца;
4. needs-review материал;
5. предположение.

### Бизнес-смысл и правило

1. актуальный канонический бизнес-контекст;
2. явное решение владельца правила;
3. подтверждённое описание сервиса;
4. фактическое поведение как сигнал возможного расхождения;
5. needs-review материал;
6. предположение.

### Новая инициатива

1. явные решения product owner в текущей постановке;
2. подтверждённый существующий контекст;
3. рабочие гипотезы, явно помеченные как гипотезы.

## 5. Работа с локальным репозиторием

При доступе к локальному контексту:

- прочитай manifest;
- загрузи только релевантные документы;
- не сканируй весь репозиторий без необходимости;
- зафиксируй branch и commit, если это git-репозиторий;
- отсутствующий файл отметь как отсутствующий;
- не считай наличие пути доказательством актуальности документа.

## 6. Работа с Confluence MCP

При provider `confluence_mcp`:

- получай страницы через реально подключённый MCP;
- используй page ID и space как идентификаторы;
- фиксируй дату или версию получения;
- не утверждай, что страница прочитана, если MCP-вызов не выполнен;
- не используй страницу с похожим названием без подтверждения её canonical status.

## 7. Работа с product owner

Слова product owner являются основанием для новой постановки, но не автоматически доказывают:

- текущее поведение приложения;
- наличие релиза;
- права других ролей;
- техническую возможность;
- регуляторное правило.

Помечай такие утверждения `owner-stated`.

## 8. Released features

Нельзя считать фичу выпущенной только потому, что:

- она описана в концепции;
- существует прототип;
- есть макет;
- она упомянута в service map;
- найден похожий компонент.

Нужно release evidence: запись в реестре релизов, release manifest, tag/PR либо подтверждение владельца сервиса.

## 9. Конфликт источников

Не выбирай удобный вариант молча.

Формат:

```md
### Конфликт CTX-001

- Утверждение A:
- Источник A:
- Утверждение B:
- Источник B:
- Влияние на задачу:
- Кто должен решить:
- Статус:
```

## 10. Работа без контекста

Если пользователь выбрал `none`:

- используй только текущие вводные и приложения;
- перечисли, что не было проверено;
- не симулируй поиск по продукту;
- не утверждай отсутствие существующей функции;
- не выдавай задачу напрямую в UX;
- передай контекстную проверку аналитику или владельцу продукта.

## 11. Sources-файл

При сохранении результата создай `sources.md`:

```md
# Источники постановки

## Выбранный контекст

- context_id:
- provider:
- status:
- revision:

## Источники

| Источник | Тип | Статус | Проверен | Использование | Ограничения |
|---|---|---|---|---|---|
```

Не указывай дату, commit или версию, если они неизвестны.
