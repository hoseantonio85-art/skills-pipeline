# UX patterns NORM

Используй паттерны как систему выбора, а не как обязательный шаблон каждого экрана. Сначала определи намерение, данные и решение пользователя; затем выбери surface.

## 1. Card registry

Основной способ показать множество рисков, мер, инцидентов и других объектов.

Строка-карточка должна помогать решить, какой объект открыть или обработать первым. Покажи название, статус/сигнал, причину внимания, 1–3 ключевых признака и доступное действие. Допускай колонкообразное выравнивание между карточками.

Не используй классическую таблицу как основной реестр. Локальная табличная сетка допустима для истории изменений и прямого сравнения однородных значений.

## 2. Page header

Покажи название рабочей области и осмысленный счётчик. Размещай справа только контекстные действия, которые относятся ко всей странице. Не перегружай header действиями над отдельными объектами.

## 3. Quick filters and attention zones

Вынеси частые и понятные пользователю способы фокусировки в chips. При необходимости покажи количество и семантический цвет. Быстрый фильтр должен запускать понятный сценарий, а не повторять случайное поле модели данных.

Поиск раскрывай по запросу, если он не является главным инструментом страницы. Полный набор фильтров открывай в drawer. Показывай компактный индикатор активного расширенного фильтра.

## 4. Dashboard

Используй для обзора ситуации, мониторинга, сравнения и поиска зон внимания. Каждый агрегат или график должен вести к фильтрации, исследованию или действию. Dashboard может сочетаться с card registry.

Не создавай декоративную стену KPI и не применяй dashboard только потому, что данных много.

## 5. Summary-first

Используй, когда пользователю иначе пришлось бы самостоятельно собирать вывод из нескольких сигналов. Summary отвечает: что происходит, почему важно и что делать дальше.

Не добавляй summary как обязательную декоративную шапку простого экрана.

## 6. Object Modal

Открывай самостоятельный объект из множества в большой modal, если важно сохранить список и его фильтры. Для последовательного разбора допускай previous/next.

Внутри Object View сначала покажи смысл и состояние объекта, затем содержание, связи и meta. Разделяй основную область и правый rail, когда это помогает сканированию.

Read-only Object View обычно не имеет footer: действия находятся в контексте объекта или rail. Create/edit использует стабильный footer для commit-действий.

## 7. Drawer

Используй для подчинённой задачи: фильтра, выбора, настройки, пояснения, поиска связи или дополнительной работы внутри modal. Drawer должен сохранять состояние родительской поверхности.

Не открывай полноценный самостоятельный объект в drawer. Не делай drawer промежуточным шагом перед Object Modal без пользовательской необходимости.

## 8. Floating action dock

Используй нижнюю плавающую панель, когда основное действие или AI/chat должно оставаться доступным при исследовании длинной поверхности. Сочетай одно primary action с ограниченным числом вспомогательных действий. Резервируй место под панель и упрощай её на mobile.

Это узнаваемый паттерн NORM, но он не нужен на экране без постоянного следующего действия.

## 9. AI blocks

Привязывай AI к конкретному объекту, ситуации или действию. Показывай полезный результат: summary, объяснение, гипотезу, рекомендацию или подготовленное действие. Обозначай неопределённость и оставляй решение человеку.

Не используй абстрактный чат без контекста как замену UX-решению.

## 10. States

- Empty объясняет, почему данных нет и какой следующий шаг доступен.
- Loading сохраняет структуру ожидаемого экрана, если это помогает ориентации.
- Error объясняет последствия и предлагает восстановление.
- Partial показывает доступные данные и явно обозначает пробел.
- Action progress предотвращает повторный запуск и сообщает результат.

## 11. Surface decision

Перед проектированием ответь:

1. Пользователь обозревает множество, исследует объект или выполняет подчинённую задачу?
2. Нужно ли сохранять исходный контекст?
3. Какой сигнал влияет на решение?
4. Какое действие завершает сценарий?

Выбери:

- page — самостоятельная рабочая область;
- card registry — принятие решений по множеству;
- dashboard — обзор и зоны внимания;
- Object Modal — самостоятельный объект поверх множества;
- drawer — подчинённая задача;
- regular modal — короткое решение или компактная форма;
- inline — локальная деталь или действие.

## Anti-patterns

- равнозначный набор блоков без информационного приоритета;
- классическая таблица как основной список объектов;
- карточки, показывающие все поля без отбора;
- summary, не уменьшающая работу интерпретации;
- dashboard без drill-down или действия;
- самостоятельный объект в drawer;
- read-only Object View с дублирующим footer;
- смешивание content и технической meta;
- цвет как единственный носитель статуса;
- дублирование одного действия в нескольких местах без причины;
- AI без контекста и понятной ценности.
