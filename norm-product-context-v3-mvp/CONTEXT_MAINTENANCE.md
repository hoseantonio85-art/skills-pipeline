# Поддержка и развитие контекста

## 1. Два слоя

### Нормализованный слой

`product-system/` содержит короткие канонические документы, пригодные для загрузки моделью. Здесь не должно быть длинных стенограмм, исходного кода библиотек и повторяющихся инструкций.

### Evidence layer

`sources/` содержит исходные файлы, пакеты и полные нормативные документы. Они подтверждают происхождение знания и читаются только точечно.

## 2. Как добавить новый сервис

1. Создать `product-system/02_services/<service>.md`.
2. Добавить сервис в `services_map.md`.
3. Добавить запись в `07_business_context/service_registry.yaml`.
4. Обновить роли, glossary, capabilities и rules только если появились новые подтверждённые факты.
5. Обновить source registry и запустить validation.

## 3. Как добавить UX/UI pattern

1. Добавить нормализованный pattern в `product-system/04_ui/patterns/`.
2. Зарегистрировать его в `pattern-registry.yaml`.
3. Указать `use_when`, `do_not_use_when`, структуру, ограничения и source references.
4. Не добавлять pattern в автоматический профиль, если он нужен только отдельным задачам.

## 4. Как обновить UI Kit

1. Положить новый package в `sources/ui-kit/`.
2. Обновить `ui_sources.yaml` и `ui_context_status.md`.
3. Перегенерировать `component-index.yaml` по exports/types новой версии.
4. Проверить изменения props и enums.
5. Не удалять предыдущую версию, пока не подтверждена миграция всех prototype workspaces.

## 5. Как подключить продуктовые repositories

Не копируйте большие repositories внутрь context archive. Добавляйте их в source registry как внешние providers с revision и allowed usage. Для MVP этапа 03 полное сканирование frontend repositories запрещено.

## 6. Правило актуальности

Каждое новое знание должно иметь:

- источник;
- статус проверки;
- дату обновления;
- владельца или роль, которая должна подтвердить факт;
- область действия.

Не исправляйте конфликтующие источники молча. Зафиксируйте конфликт в `product_decisions.md` или task increment.

## 7. Версионирование

- patch — уточнение текста без изменения контрактов загрузки;
- minor — новый документ, сервис, pattern или source;
- major — изменение manifest schema, profile contracts или структуры путей.
